Software-Defined Networking

2026, August 30

Software-Defined Networking: From Application Intent to the Final Packet

Terminology: The architecture is normally called SDN, Software-Defined Networking, not SDM.

SDN is a programmable networking architecture in which the logic that decides how traffic should behave is separated from the machinery that forwards actual packets.

Reference: RFC 7426: Software-Defined Networking Layers and Architecture Terminology.

1. The Complete SDN Mental Model

Imagine a railway system:

  • Passengers and cargo: Packets carrying application data.
  • Railway tracks: Physical or logical network links.
  • Junctions: Switches, routers, gateways, and virtual switches.
  • Signals at each junction: Forwarding rules.
  • Railway control centre: SDN controller.
  • Business requirements: Network applications, intent, and policies.
  • Sensors reporting track conditions: Telemetry and topology events.

The control centre does not physically carry every train. It studies the railway map, calculates routes, and configures signals at junctions. Once the signals are configured, trains move through the junctions independently.

Application expresses intent
        |
        v
Controller converts intent into network decisions
        |
        v
Devices convert decisions into local forwarding rules
        |
        v
Data plane applies those rules to packets
        |
        v
Telemetry reports what actually happened

1.1 The Most Important SDN Principle

Normal user packets do not travel through the SDN controller.

User packets travel through:

  • Physical switches
  • Routers
  • Virtual switches
  • SmartNICs and DPUs
  • Firewalls
  • Gateways
  • Load balancers
  • Other forwarding elements

The controller receives information such as:

  • Link and port status
  • Topology information
  • Traffic counters
  • Queue usage
  • Routing information
  • Endpoint location
  • Exceptional packet copies
  • Packets for which no existing rule matched

The controller then installs, modifies, or removes forwarding rules. Sending every packet through the controller would make the controller a bottleneck and destroy the primary performance advantage of SDN.

2. What Problem Does SDN Solve?

2.1 Traditional Networking

In a traditional network, every router or switch contains both its own control logic and forwarding machinery.

Traditional network device
+----------------------------------+
| Control plane                    |
| - Learns routes                  |
| - Runs routing protocols         |
| - Calculates preferred paths     |
+----------------------------------+
| Data plane                       |
| - Forwards packets               |
| - Applies local forwarding table |
+----------------------------------+

For example, every router may independently:

  1. Discover neighbouring routers.
  2. Exchange routes using OSPF, IS-IS, or BGP.
  3. Build its own routing database.
  4. Select preferred routes.
  5. Install those routes in forwarding hardware.
Router 1 = local brain + forwarding machinery
Router 2 = local brain + forwarding machinery
Router 3 = local brain + forwarding machinery

The complete network behaviour emerges from many independently operating devices exchanging information.

2.2 Software-Defined Networking

In SDN, network-wide decision logic is exposed through a programmable control platform.

                Shared control logic
                       |
        +--------------+--------------+
        |              |              |
     Switch 1       Switch 2       Switch 3
     data plane     data plane     data plane

The controller obtains an abstract network-wide view and calculates behaviour for multiple devices.

This does not require every local routing or protection function to disappear. Real SDN devices may still retain local functions for:

  • Basic controller reachability
  • BGP peering
  • Link failure detection
  • Local fast failover
  • Neighbour discovery
  • Basic forwarding during controller failure

2.3 The Precise Difference

Traditional network:
Network intelligence is primarily distributed among devices.

Software-defined network:
Network-wide intent and control are exposed through
programmable, logically centralized abstractions.

Logically centralized does not mean that only one physical controller server exists. A controller can be a distributed cluster spread across multiple servers, availability zones, regions, or data centres.

Systems such as Onix model the controller as a distributed system with a network-wide view and configurable trade-offs among consistency, durability, and scalability.

Reference: Onix: A Distributed Control Platform for Large-Scale Production Networks.

3. Where Does SDN Sit in the OSI Model?

SDN is not an additional OSI layer.

It is an architecture that controls behaviour across several networking layers.

Layer or Context What SDN May Control
Layer 1 Optical circuits, wavelengths, radio resources, and physical paths
Layer 2 MAC forwarding, VLANs, bridging, and Ethernet segments
Layer 3 IP routes, VRFs, MPLS labels, and tunnels
Layer 4 TCP and UDP port-based policies, forwarding, and load balancing
Layers 4 to 7 Firewalls, NAT, proxies, load balancers, and service chains
Management Configuration, certificates, software state, and telemetry
Application Connectivity intent, security policy, traffic engineering, and business requirements

The controller itself normally communicates using ordinary networking protocols carried over TCP, TLS, HTTP, gRPC, or related transports.

However, the instructions sent by the controller may control Layer 2, Layer 3, Layer 4, queues, tunnels, labels, and programmable packet-processing pipelines.

Therefore, SDN is described using architectural planes and interfaces, not as one OSI layer.

4.3 Flow

In SDN, a flow is an equivalence class of packets selected by a rule. It does not necessarily mean one TCP connection.

Examples of flows:

All packets belonging to tenant 42

All HTTPS traffic sent to 10.20.0.0/16

All packets entering switch port 7

All packets carrying VXLAN VNI 5000

All packets sent from the Finance security group

All packets with destination TCP port 443

  • RIB, Routing Information Base: Routes known to the control plane.
  • FIB, Forwarding Information Base: Optimized entries used by the data plane to forward packets.

4.5 Underlay

The underlay is the physical or transport network that provides basic reachability.

Example underlay:
Physical leaf-spine IP fabric

4.6 Overlay

The overlay is a logical network created over the underlay.

Example overlay:
Tenant VXLAN network carried over a physical IP fabric

4.7 Tunnel

A tunnel places one packet inside another packet.

Outer packet:
Used by the transport underlay

Inner packet:
Original tenant or application traffic

4.8 VTEP

A VXLAN Tunnel Endpoint encapsulates and decapsulates VXLAN traffic.

A VTEP may live in:

  • A physical leaf switch
  • A hypervisor virtual switch
  • A software router
  • A gateway
  • A SmartNIC or DPU

VXLAN creates logical Layer 2 segments over a Layer 3 transport network. A VXLAN Network Identifier, or VNI, identifies the logical segment.

Reference: RFC 7348: Virtual eXtensible Local Area Network.

4.9 Intent

Intent describes what outcome is required, not every individual device command.

Intent:

Application A may communicate with Database B,
but only through Firewall F,
with at least 2 Gbit/s bandwidth,
and without using jurisdiction X.

The controller translates this into paths, ACLs, tunnel mappings, queues, meters, and device-specific entries.

5. The Planes of an SDN System

Plane Fundamental Question Main Responsibility
Application plane What should the network accomplish? Routing applications, security policy, traffic engineering, access control, and service requirements
Control plane How should the network accomplish it? Topology, path selection, policy resolution, and forwarding-rule calculation
Management plane How should devices be configured and observed? Configuration, inventory, certificates, software state, and telemetry
Operational plane What resources and operational state currently exist? Ports, queues, interfaces, capabilities, faults, and device health
Forwarding or data plane What should happen to this packet now? Match, modify, forward, replicate, meter, queue, encapsulate, or drop

5.1 Application Plane

The application plane expresses desired network behaviour.

Examples:

  • Shortest-path routing
  • Zero-trust segmentation
  • Load balancing
  • Service chaining
  • Traffic engineering
  • DDoS mitigation
  • Quality of service
  • Tenant network creation
  • Energy-aware routing
Permit:
Employee devices -> Payroll application -> TCP 443

Deny:
Guest network -> Payroll application -> all protocols

5.2 Control Plane

The control plane transforms policy into network-wide decisions.

It answers questions such as:

  • Which endpoints exist?
  • Where are those endpoints attached?
  • Which links are currently available?
  • What are their capacity and latency?
  • Which paths satisfy policy?
  • What rules must be installed on each device?
  • What should happen after a failure?
  • Which controller currently owns each device?

5.3 Management Plane

The management plane handles device configuration and observation.

For example, gNMI supports operations for:

  • Retrieving configuration
  • Modifying configuration
  • Receiving streaming telemetry

Reference: gNMI Specification.

5.4 Data Plane

The data plane executes already-calculated behaviour at packet speed.

7. SDN Is Not a Topology

SDN is a control architecture. Star, tree, ring, mesh, leaf-spine, and Clos are topologies.

SDN can control any of these topologies.

7.1 Physical or Underlay Topology

Let:

$$G_P=(V_P,E_P)$$

  • $V_P$: Physical switches, routers, gateways, hosts, and other nodes.
  • $E_P$: Physical or transport links.
Leaf 1 ----- Spine 1 ----- Leaf 3
   \          |            /
    \         |           /
     ----- Spine 2 -------

7.2 Logical Overlay Topology

Let:

$$G_O=(V_O,E_O)$$

This graph represents logical entities such as:

  • Tenant networks
  • Virtual routers
  • VXLAN segments
  • VPNs
  • Security zones
  • Service chains

Two virtual machines may appear to be directly connected at Layer 2 even though their packets cross several physical switches.

7.3 Control Topology

Let:

$$G_C=(V_C,E_C)$$

The control topology contains:

  • Controller instances
  • Managed devices
  • Controller-to-device channels
  • Controller-to-controller channels
  • Management systems

The control topology may use:

  • A separate out-of-band network
  • The same in-band production network
  • A combination of both

A service graph describes the required processing order.

11.4 Highest-Priority Match

If packet $p$ matches multiple rules, the selected rule can be represented as:

$$ r^*= \arg\max_{r\in R,\;M_r(p)=1} \operatorname{priority}(r) $$

  • $R$: Set of rules in the current table.
  • $M_r(p)=1$: Packet $p$ matches rule $r$.
  • $r^*$: Highest-priority matching rule.

11.5 Common Actions

A matched rule may:

  • Output the packet to a port
  • Drop the packet
  • Send a copy to the controller
  • Modify a MAC address
  • Modify an IP address
  • Push or remove a VLAN tag
  • Push or remove an MPLS label
  • Encapsulate the packet into a tunnel
  • Select a load-balancing group
  • Select a failover group
  • Apply a rate meter
  • Assign an egress queue
  • Continue processing in another table

11.6 Table Miss

When no normal rule matches, the table-miss behaviour may:

Drop the packet

Continue to another table

Send packet information to the controller

Apply a configured default action

A table miss does not always mean that the packet is sent to the controller.

13.2 Link Discovery Using LLDP

1. Controller instructs Switch A to emit an LLDP frame
   from port 3.

2. Switch B receives the LLDP frame on port 7.

3. Switch B reports the received discovery information
   to the controller.

4. Controller records:

   Switch A, port 3 <-> Switch B, port 7

The controller repeats this process to build a graph of switches and links.

14. How the Controller Calculates a Path

Let $\mathcal{P}(s,d)$ represent all possible paths from source $s$ to destination $d$.

A simple controller may compute:

$$ p^* = \arg\min_{p\in\mathcal{P}(s,d)} \sum_{e\in p} w(e) $$

A production controller may solve a constrained optimization problem:

$$ \begin{aligned} \text{minimize } & C(p) \\ \text{subject to }& \operatorname{bandwidth}(p)\geq B_{\min}\\ &\operatorname{latency}(p)\leq L_{\max}\\ & p \cap F_{\text{forbidden}}=\varnothing\\ &\operatorname{failureDomain}(p_1) \neq \operatorname{failureDomain}(p_2) \end{aligned} $$

The word “shortest” may mean:

  • Fewest hops
  • Lowest latency
  • Lowest congestion
  • Lowest monetary cost
  • Highest reliability
  • Policy-compliant path
  • Geographically compliant path
  • Energy-efficient path

14.1 Compiling a Global Path into Local Rules

Network-wide path:

A -> Switch 1 -> Switch 4 -> Switch 8 -> B

The controller converts the global path into local instructions:

Switch 1:
Destination B -> output toward Switch 4

Switch 4:
Destination B -> output toward Switch 8

Switch 8:
Destination B -> output toward Host B

Each switch only needs enough information to perform its local part of the global decision.

  • Stage inactive rules
  • Wait for acknowledgements
  • Use barriers or transactions
  • Activate a version only after all required devices are ready

15.9 Phase 9: Packet Forwarding

Packets now use the installed data-plane rules. The controller is not consulted for every packet.

15.10 Phase 10: Telemetry and Reconciliation

Devices report:

  • Link failures
  • Port state
  • Flow counters
  • Queue depth
  • Packet loss
  • Table changes
  • Errors
  • Flow expiration

The controller recomputes behaviour when observed state differs from desired state.

18. Packet Flow When No Rule Exists

18.1 Reactive Workflow

1. Packet enters switch.

2. No normal flow entry matches.

3. Table-miss rule generates a Packet-In event.

4. Switch may buffer the original packet.

5. Controller receives packet headers, metadata,
   or a packet copy.

6. Controller checks topology and policy.

7. Controller calculates a path.

8. Controller sends flow-modification instructions
   to relevant devices.

9. Controller sends a Packet-Out instruction
   or references the buffered packet.

10. Switch forwards the first packet.

11. Later matching packets use installed rules directly.

OpenFlow allows the switch to buffer the original packet and send the controller only a portion of the packet plus a buffer identifier.

18.2 First-Packet Latency

For a reactive flow:

$$ T_{\text{first}} = T_{\text{ingress}} + T_{\text{packet-in}} + T_{\text{decision}} + T_{\text{flow installation}} + T_{\text{resume}} $$

For subsequent packets:

$$ T_{\text{subsequent}} \approx T_{\text{data-plane path}} $$

This is why important or predictable traffic is often handled using proactive rules.

19. Proactive, Reactive, and Hybrid Forwarding

19.1 Proactive Forwarding

Rules are installed before packets arrive.

Advantages:

  • No controller round trip for the first packet
  • Predictable latency
  • Better resistance to Packet-In storms
  • Suitable for known routes and security policies

Costs:

  • More preinstalled state
  • Possibly unused entries
  • Greater table-capacity consumption

19.2 Reactive Forwarding

Rules are installed after a new flow or exception appears.

Advantages:

  • Fine-grained decisions
  • Less unused forwarding state
  • Dynamic per-flow policy

Costs:

  • First-packet latency
  • Higher controller load
  • Greater dependency on control-channel availability

19.3 Hybrid Forwarding

28. Failure Workflow

28.1 Link Failure

Suppose the active path is:

28.1.1 Immediate Local Reaction
Leaf 1 -> Spine 2 -> Leaf 2

A preinstalled fast-failover rule may select the backup without waiting for the controller.

28.1.2 Global Controller Reaction
  1. The device reports the link failure.
  2. The controller removes the failed edge from its topology.
  3. The controller recomputes affected paths.
  4. The controller checks capacity and policy.
  5. The controller installs optimized replacement state.
  6. The controller removes obsolete entries.
Fast local protection:
Immediate device-local timescale

Global optimization:
Controller convergence timescale

28.2 Controller Failure

Existing data-plane rules may continue forwarding packets.

  • Install new reactive flows
  • Process global topology changes
  • Change policy
  • Recompute paths
  • Renew expiring entries

A backup controller can assume ownership.

28.3 Fail-Secure and Fail-Standalone

  • Fail-secure: Existing entries continue, but packets needing unavailable controller intervention are generally dropped.
  • Fail-standalone: The device may revert to conventional switching or routing behaviour.

29. The Consistent-Update Problem

Suppose traffic currently follows:

Old path:
A -> X -> Y -> B

The controller wants to move traffic to:

New path:
A -> P -> Q -> B

If devices update at different times, a packet may experience a mixed configuration.

A uses new rule.

P still has an older rule.

Y has already removed the old rule.

Possible transient failures include:

  • Forwarding loop
  • Black hole
  • Policy bypass
  • Duplicate delivery
  • Congestion
  • Incorrect service-chain order

29.1 Unsafe Update

Delete old rules
        |
        v
Install new rules

This may create a temporary gap.

29.2 Ordered Update

For a simple path, the controller can install from the destination backward:

1. Prepare Q.

2. Prepare P.

3. Change A.

4. Remove obsolete X and Y state.

29.3 Versioned Update

1. Install all version-2 rules.

2. Mark new packets as version 2 at ingress.

3. Allow version-1 packets to finish.

4. Remove version-1 rules.

Each packet then experiences either the complete old configuration or the complete new configuration, rather than an arbitrary mixture.

Reference: Consistent Updates for Software-Defined Networks.

30. How Traffic Engineering Works

Assume two paths:

Path P1:
A -> B -> D
Capacity = 10 Gbit/s
Current load = 9 Gbit/s

Path P2:
A -> C -> D
Capacity = 20 Gbit/s
Current load = 5 Gbit/s

A shortest-hop algorithm may treat both paths equally.

A utilization-aware controller may define link cost as:

$$ w(e)=\frac{1}{C_e-U_e} $$

  • $C_e$: Link capacity.
  • $U_e$: Current utilization.

As a link becomes more congested, its calculated cost increases.

The controller may divide traffic by:

  • Flow
  • Prefix
  • Tenant
  • Application
  • Traffic class
  • Hash group
  • Explicit tunnel

The controller should not react to every tiny utilization fluctuation because excessive sensitivity causes route oscillation.

Practical control systems use:

  • Smoothing
  • Hysteresis
  • Minimum hold times
  • Thresholds
  • Predictive models
  • Rate-limited reconfiguration

Observe
   |
   v

   |
   v

   |
   v

Let:

  • $D(t)$: Desired network state.
  • $O(t)$: Observed network state.
  • $A(t)$: Corrective action.

Then:

$$ A(t)=K(D(t)-O(t)) $$

The symbolic difference $D(t)-O(t)$ represents failure, drift, congestion, or policy mismatch. $K$ represents the controller logic that produces corrective action.

  • Partial writes
  • Controller crashes

  • Network partitions
  • Stale topology
  • Conflicting applications
  • Concurrent updates

An SDN controller is not merely a centralized router. It is a distributed system coordinating another distributed system: the forwarding fabric.

36. Formal Model of an SDN Network

At time $t$, define the network state as:

$$ S(t)= \left[ T(t), E(t), P(t), F(t), Q(t), C(t) \right] $$

  • $T(t)$: Topology state.
  • $E(t)$: Endpoint and reachability state.
  • $P(t)$: Policy state.
  • $F(t)$: Installed forwarding state.
  • $Q(t)$: Queue and resource state.
  • $C(t)$: Controller-cluster state.

36.1 Imperfect Observation

The controller observes an imperfect projection:

$$ O(t)=H(S(t-\delta))+\epsilon $$

  • $\delta$: Observation delay.
  • $\epsilon$: Missing, stale, or incorrect information.
  • $H$: Telemetry and discovery process.

36.2 Policy Computation

The controller computes:

$$ D(t)=\Pi(O(t),I) $$

  • $I$: Operator intent.
  • $\Pi$: Policy and path-computation function.

36.3 Device Compilation

The controller generates updates:

$$ U(t)=\mathcal{C}(D(t),K) $$

$K$ represents device capabilities and limitations.

36.4 Asynchronous Application

Devices apply updates asynchronously:

$$ F(t+\Delta)=\mathcal{A}(F(t),U(t)) $$

The central difficulty is that $\Delta$ differs across devices, messages may fail, and topology may change while an update is being installed.

37. SDN Correctness Properties

37.1 Reachability

Permitted traffic must have a valid path:

$$ \operatorname{allowed}(s,d) \Rightarrow \exists p:s\leadsto d $$

37.2 Isolation

Forbidden endpoints or tenants must not communicate:

$$ \operatorname{forbidden}(s,d) \Rightarrow \nexists p:s\leadsto d $$

37.3 Waypoint Compliance

Traffic must pass through required network functions in the correct order:

$$ p(s,d) \supseteq [F_{\text{firewall}},F_{\text{IDS}}] $$

37.4 Loop Freedom

A packet should not revisit the same forwarding state indefinitely.

37.5 Black-Hole Freedom

A permitted packet should not reach a device where no valid next action exists.

37.6 Per-Packet Consistency

Every packet should experience one coherent network-policy version.

37.7 Capacity Safety

For every link $e$:

$$ \sum_{f:e\in p_f}x_f \leq \operatorname{capacity}(e) $$

37.8 Convergence

After a finite set of failures or policy changes, the control system should eventually reach a stable valid state.

37.9 Availability During Controller Loss

Critical data-plane behaviour should continue for an appropriate period when active controller communication is unavailable.

38. SDN Compared with Related Concepts

38.1 SDN versus OpenFlow

SDN:
Architectural idea

OpenFlow:
One controller-to-switch protocol and switch model

SDN can exist without OpenFlow.

38.2 SDN versus P4

SDN:
Separation and programmability of network control

P4:
Language for defining programmable data-plane behaviour

P4 can be used within an SDN architecture.

38.3 SDN versus NFV

SDN:
Controls paths and forwarding behaviour

NFV:
Runs network functions as software
instead of fixed-purpose appliances

They frequently work together:

NFV creates a software firewall.

SDN steers traffic through that firewall.

38.4 SDN versus Network Automation

A script that logs into routers and enters CLI commands is automation.

An architecture becomes closer to SDN when it uses:

  • Network-wide abstractions
  • Programmable interfaces
  • Separation of intent and forwarding
  • Model-based control
  • Closed-loop observation and reconciliation

38.5 SDN versus SD-WAN

SDN:
Broad programmable network architecture

SD-WAN:
Application of SDN principles to wide-area networking

38.6 SDN versus Cloud Virtual Networking

A cloud virtual network is commonly an SDN-created logical network.

The user sees:

Subnets
Security groups
Routes
Gateways
Load balancers

The cloud provider translates those abstractions into:

Virtual-switch rules
Tunnels
Distributed routing
Firewall state
Physical-fabric forwarding

39. Common SDN Misconceptions

39.1 “The Controller Forwards All Packets”

False. Normal packets remain in the data plane.

39.2 “The Controller Is One Physical Machine”

False. It is logically centralized and may be implemented as a distributed cluster.

39.3 “SDN Is a Star Topology”

False. SDN can control star, mesh, tree, ring, Clos, leaf-spine, and other topologies.

39.4 “SDN Switches Are Dumb”

False. Data planes may perform sophisticated parsing, matching, encapsulation, metering, load balancing, queueing, and local failover.

39.5 “Control and Data Planes Must Use Different Cables”

False. The control channel may be out-of-band, in-band, or hybrid.

39.6 “Every Table Miss Goes to the Controller”

False. A table miss may be dropped, passed to another table, handled locally, or sent to the controller.

39.7 “SDN Removes BGP and OSPF”

False. SDN can coexist with, configure, consume, or supplement distributed routing protocols.

39.8 “Overlay and Underlay Are the Same Network”

False. The overlay is a logical network carried by the underlay.

39.9 “The Controller Has Perfect Real-Time Knowledge”

False. Controller state is delayed, replicated, and potentially stale.

39.10 “OpenFlow Is SDN”

False. OpenFlow is one mechanism within the larger SDN architecture.

39.11 “Northbound Means Traffic Moving North”

False. Northbound describes an API relationship. North-south data-centre traffic is a separate concept.

40. Complete End-to-End SDN Chain

1. An application expresses network intent.

2. The controller authenticates and validates the intent.

3. The controller reads topology, endpoint, policy,
   capability, and resource models.

4. It calculates a valid path and service placement.

5. It compiles the network-wide decision into local rules.

6. Southbound and management interfaces deliver the rules.

7. Each switch stores rules in its local data-plane tables.

8. A packet enters an ingress port.

9. The local parser extracts headers and metadata.

10. Match-action tables classify, permit, modify, route,
    encapsulate, meter, queue, or drop the packet.

11. The packet leaves through an egress port.

12. Every intermediate device repeats local data-plane processing.

13. For overlays, the ingress tunnel endpoint encapsulates.
    The underlay forwards using outer headers.
    The destination tunnel endpoint decapsulates.

14. For external traffic, the packet reaches a border gateway,
    where routing, security, and optional NAT are applied.

15. BGP exchanges external reachability with other networks.

16. Counters, link events, and telemetry return to the controller.

17. The controller compares observed state with desired state.

18. On failure, congestion, or drift, the controller computes
    and safely installs an updated configuration.

40.1 Irreducible SDN Model

$$ \boxed{ \text{Intent} \rightarrow \text{Controller decision} \rightarrow \text{Per-device rules} \rightarrow \text{Distributed data-plane execution} \rightarrow \text{Telemetry} \rightarrow \text{Reconciliation} } $$
